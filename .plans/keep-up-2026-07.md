# Keep-up pass 2026-07 — rackctl

Re-sync rackctl with what the org ships today. rackctl is an **orchestrator**: it
clones and drives `landing-zone`, `eks-gitops` and `eks-agent-platform` and never
forks or vendors them — so "keeping up" means the seams rackctl reaches through
must still exist, and the README must describe the tool that exists rather than the
one that was designed.

**Nothing is deployed today** — no live hub cluster. Design for the cleanest shape;
no migration/backward-compat framing anywhere (greenfield doctrine).

## Target 1 — `model-import` as a gated opt-in (S)

**Depends on:** landing-zone `cddbe8f` ("Add the model-import component for Bedrock
Custom Model Import"), merged. Confirm the component's inputs by reading the merged
`components/aws/model-import/variables.tf` directly.

**Findings:** `components/aws/model-import` creates exactly two things plus discovery
metadata — the S3 staging bucket `<account>-<region>-model-import` and the IAM role
`model-import-<region>` Bedrock assumes during `CreateModelImportJob` — and publishes
both to SSM under `/eks-agent-platform/model-import/`. It takes **no** per-run inputs
(`environment` and `region` come from `live/root.hcl`; `team` is set in the
`_envcommon`), so a plain boolean gate is a complete interface — there is nothing for
a pointer-struct in the `dns` idiom to carry. Its live leaf declares no `dependency`
block and the component reads only `aws_caller_identity` / `aws_partition`, so unlike
`managed-monitoring` (whose position is load-bearing because `cluster-bootstrap` reads
its SSM params) its position in the apply order is not a constraint.

Two hazards are load-bearing. The component's own header states that an imported
Bedrock model is an account+region resource that outlives any one cluster and that
"tearing a cluster down must not orphan or destroy a model another cluster is
serving". And the staging bucket is versioned with no `force_destroy`, so once any
weights are staged a `terragrunt destroy` fails `BucketNotEmpty` — which in a reverse
teardown halts the loop with the EKS cluster and VPC still standing and billing.

`eks-agent-platform/docs/runbooks/import-open-weight-model.md` names the component as
a hard prerequisite and pins Custom Model Import to four regions.

**Approach:**
1. `AgentPlatform.ModelImport bool` (`modelImport`), off by default — not added to
   `Default()`, so the zero value is the default.
2. `Validate`: reject `modelImport` with `agentPlatform.enable: false`, and reject a
   `cloud.region` outside `bedrockCustomModelImportRegions`. Provisioning the bucket
   and role outside those regions *succeeds* in Terraform and is silently useless,
   which is exactly the failure class this repo's validation exists to kill.
3. `CoreComponents` appends `model-import` last among the conditionals, which puts it
   in `substrateComponents` automatically (that set is derived, never restated).
4. `KeepOnDestroy(component)` — a new, deliberate apply/destroy asymmetry — consulted
   by **both** `substrate.Teardown` and the `rackctl destroy` loop, each printing what
   survives and how to remove it deliberately.

**Acceptance:** `make test vet fmt` green; a default dry-run does not mention
`model-import`; `modelImport: true` in `eu-west-1` fails validation before any phase
runs; `KeepOnDestroy` is true for `model-import` and false for every other component.

**Shipped.** As designed. Discoveries:

- **The imported-model grant is blocked in TWO repos, not one, so the note names both.**
  landing-zone's `agent-iam` expands `bedrock_allowed_model_ids` only to
  `foundation-model/<id>` and `inference-profile/*<id>` ARNs — its own variable doc
  says custom/imported models are not matched, and the only in-tree lever is the
  empty-list escape hatch that widens every tenant role in the account to
  `Resource = "*"`. Independently, the operator's own `bedrock-model-scoping` inline
  policy is a `Deny` with `NotResource` set to that same expanded ARN list, so it
  excludes an imported-model ARN even if landing-zone's baseline allowed it. So
  `modelImport: true` provisions the **substrate** and nothing else; an `imported`
  ModelGateway route gets `AccessDenied` at `InvokeModel` until both repos change
  together. The phase-4 note says exactly that rather than implying a working path.
- **The keep-set needed a negative test, not just a positive one.** The existing
  `TestSubstrateComponents_IsSubsequenceOfCore` asserts the *apply* lists only and
  structurally cannot catch a mistake in the destroy path. `TestModelImport_IsAppliedButNeverDestroyed`
  therefore also asserts that no *other* component is in the keep-set — if `cluster`
  or `network` were ever added, a failed init would leave a VPC and an EKS control
  plane billing forever.
- **`CoreComponents` has a third consumer, and the carve-out did not reach it.**
  `preflight.CheckStaleState` walks the same list looking for components that still hold
  tfstate after the cluster is gone. model-import's state survives a teardown *by design*,
  so the check would have failed forever after the first `rackctl destroy` — and because
  `init --apply` runs the preflight as a gate, rackctl would have refused to provision
  ever again over a bucket it was built to keep. Found by adversarial review. This is the
  same failure class as the original "restating the component list" bug, one level up:
  the list is shared, so the exclusion has to be too.

## Target 2 — phase 9 vs. the current tenant model (M)

**Depends on:** eks-agent-platform `main` (the datastores / capabilities /
directSecretReads vocabulary, landed 2026-07-23).

**Findings:** phase 9 **could never have succeeded**, and no test covered it. The
dry-run prints its real argv, and all three lines are wrong:

- `charts/tenant` nests its values under `platform.` — `platform.name`,
  `platform.tenant`, `platform.persona`. rackctl passed bare `tenant=` and `persona=`
  and never passed `platform.name` at all, so helm accepted three orphan values no
  template reads and the render died on the chart's own
  `fail "platform.name is required"` guard. Verified by running helm directly.
- A `Platform` never gets a `Ready` **condition**. The operator reports readiness as
  `status.phase == "Ready"`; the only conditions it writes are `Suspended`,
  `ModelAccessScoped`, `NamespaceReady` and `VClusterReady`. `--for=condition=Ready`
  blocks the full 15m against a tenant that is already up.
- Neither call passed `-n`. The chart plants its CRs in `controlPlaneNamespace`
  (default `eks-agent-platform`), not the Helm release namespace.

On the README's framing: the "5-step `extraPolicyArns` dance" is stale, but **not**
because `extraPolicyArns` was replaced. An adversarial check found it live,
undeprecated, still reconciled on both IAM paths, and still the only identity grant
seam `charts/tenant` emits — `capabilities` / `datastores` / `directSecretReads` were
added *alongside* it. The bullet is stale for a stronger reason: phase 9 has never
contained any `extraPolicyArns` logic or ordering enforcement at all
(`grep extraPolicyArns internal/` returns nothing), so both the bullet and the phase
table's "enforcing the app-seam order" advertise code that does not exist.

**Approach:**
1. Drive `charts/tenant` on its real value paths; pass the namespace as **both**
   `--namespace` and `--set controlPlaneNamespace=` from one package const so release
   and objects can never diverge.
2. Wait on `--for=jsonpath={.status.phase}=Ready -n <ns>`.
3. Add `smoke.Teardown` (`helm uninstall`), mirroring `portal.Teardown`.
4. Print an honest note about what the phase does and does not prove.
5. `smoke_test.go` pinning the argv, in the repo's fake-binary-on-PATH idiom.

**Acceptance:** `make test vet fmt` green; the dry-run's phase-9 helm line contains
`--set platform.name=` and no bare `--set tenant=`; the kubectl line waits on
`jsonpath={.status.phase}=Ready` in `eks-agent-platform`.

**Shipped.** As designed. Discoveries:

- **`smoke.Teardown` is load-bearing, not tidiness.** The engine tears completed
  phases down in reverse, so deleting the Platform lets the operator's finalizer drop
  the per-tenant IAM role *while the operator is still running to do it*. A surviving
  role attaches the tenant baseline policy that the substrate phase's `agent-iam`
  destroy must delete, and that fails `DeleteConflict` — halting the teardown with the
  cluster half-gone.
- **rackctl cannot express the new tenant vocabulary, and must say so rather than
  work around it.** `charts/tenant` emits no `spec.datastores`, no
  `spec.identity.capabilities`, no `spec.identity.directSecretReads`, and `--set` on
  those paths is silently discarded (verified: the render is byte-identical). Building
  the CR trio inside rackctl would move the tenant's canonical shape into this repo
  and diverge from what the portal vends — a fork in all but name. The phase states
  the limit instead. Fixing the chart is upstream work.
- **The phase was silently ignoring two config fields the chart *does* expose.**
  `agentPlatform.bedrockModelFamilies` and `agentPlatform.compliance` are declared,
  defaulted and documented, and `charts/tenant` has exactly the matching value paths —
  but nothing passed them, so the first tenant was vended against chart defaults that a
  config could contradict outright (`hipaa: true` producing a Platform with
  `hipaa: false`). Both are now passed and asserted. Rendering a tenant that disagrees
  with the config that asked for it is the failure class the rest of this repo exists to
  kill, and phase 9 is the worst place to do it: it is the run's proof that vending works.

## Target 3 — live-root guard (S)

**Findings:** found while answering "what happens in an environment landing-zone has
no `model-import` leaf for". The answer turned out to matter for a component rackctl
already applies **by default**: `agent-iam`, `github-oidc` and `model-import` all have
live roots only under `workload-development`. `componentDir` is a bare `fmt.Sprintf`
with no existence check and nothing in preflight stats a component path, so a default
`rackctl init --apply` with `environment: staging` builds a VPC and an EKS control
plane in phase 3, hits a directory that does not exist in phase 4, and clean-on-failure
then destroys both. That is the most expensive bug in the repo and it is unrelated to
the model-import ask — the same guard fixes both.

**Approach:** `assertComponentRoots` at the tail of the acquire phase — the first
moment a landing-zone tree exists and the last before anything is provisioned. Stats
`terragrunt.hcl` (the file terragrunt itself looks for) for every component
`CoreComponents` returns, and fails naming the component, the environment, the exact
missing path, the consequence, and the config knob that turns it off. Generic rather
than a per-component environment allow-list: encoding landing-zone's live-tree shape
into rackctl is precisely the forking rackctl must not do, and a generic check keeps
working as roots are added upstream.

**Acceptance:** a staging config with a landing-zone checkout present fails in phase 1
(acquire) naming `agent-iam`, not in phase 4 (substrate) after the cluster is built.

**Shipped.** Discoveries — the first two came out of an adversarial review pass and
both were real:

- **The guard could destroy a platform it was written to protect.** Returning a plain
  error made the engine treat it as a failed provisioning phase, so `CleanOnFail` fired
  the full teardown sweep: `reap.OperatorRoles` force-deletes every IAM role under
  `/eks-agent-platform/` **account-wide**, and `reap.All` runs
  `kubectl delete platforms|tenants|nodeclaims|pvc --all -A` against whatever cluster the
  kubeconfig currently points at. An operator bootstrapping staging from a laptop still
  pointed at a healthy development cluster would have the guard fire *correctly* and then
  demolish the platform they were not touching. The guard now returns
  `engine.NoRollbackError` — the same judgement that exists for a convergence timeout,
  and a precondition check is its clearest case: there is nothing to reclaim, so a
  rollback can only destroy what this run did not create. Pinned by
  `TestAssertComponentRoots_FailureMustNotRollBack`.
- **A dry-run's verdict can only be advisory, and hard-failing one was wrong.** acquire
  *prints* the clone and the pull in dry-run rather than running them, so the tree on
  disk is either absent or arbitrarily old — a stale checkout made `rackctl init` (plan
  mode) reject a config that applies fine the moment the real pull happens. And "is there
  a checkout?" was answered by statting the directory while `cloneOrUpdate` answers it by
  `.git`, so an interrupted clone was judged as a checkout and failed on `network`, which
  every environment carries, with a remedy that could not help. Both fixed: same `.git`
  predicate, and a dry-run reports rather than fails. The `--apply`, which pulls first, is
  where it binds.
- **A whole-region miss is a different diagnosis.** `componentDir` embeds the region as
  well as the environment, so a region landing-zone carries no tree for would have been
  reported as an environment problem with a remedy that could never work — and the
  `modelImport` allow-list blesses three regions (`us-east-1`, `us-east-2`,
  `eu-central-1`) landing-zone does not currently carry a workload tree for. The guard now
  detects that case first and names `cloud.region`.
- **This is the one place asserting on error *text* is right.** The rest of the repo's
  validation tests assert only presence/absence; here the remedy sentence is the
  operator-facing payload, and a guard that fires without naming the knob to turn off
  is worthless.

## Target 4 — README + example config back to reality (S)

**Findings:** the phase table describes a pipeline that does not exist. `All()` is
`preflight, acquire, identity, cluster, substrate, gitops, platform, fleet, portal,
smoke` — there is no `addons` phase (it was split into `substrate` + `gitops` in #30),
so rows 4/5/6 and every parenthetical phase number in "Footguns" are wrong.

The IRSA-substitution bullet — the README's *first* advertised footgun — describes a
mechanism that now matches nothing. eks-gitops commit `f49dfd5` ("Bind cluster addons
to their IAM roles via EKS Pod Identity") removed the `000000000000` placeholders: 113
`values-<env>.yaml` files, zero placeholders. The account id now rides annotations on
the ArgoCD cluster Secret that `cluster-bootstrap` publishes, and
`addons/ai-platform/operator/values.yaml` says outright that the account id must never
be committed to the public catalog. `gitops.WriteBack` always returns `(0, nil, nil)`.

**Approach:** fix the table rows; replace the IRSA bullet with the annotation channel
that actually carries the account id; replace the tenant bullet with the two real
traps phase 9 now kills; add bullets for the account-scoped-substrate asymmetry and
the live-root guard. Make the writeback's zero-match case say plainly why it matched
nothing — behaviour unchanged, output honest.

**Acceptance:** every phase number in the README cross-checks against `phases.All()`.

**Shipped.** As designed. Discoveries:

- **Deleting `internal/gitops` was tempting and wrong for this pass.** It is dead
  against the current catalog, but removing it removes a git commit+push side effect
  that a private fork carrying literal placeholders would still need. The honesty gap
  is closed by making the code and the README describe what actually happens; whether
  the writeback should exist at all is a separate decision with its own risk surface.

## Reported upward (not fixed here — rackctl orchestrates, it does not fork)

- **eks-agent-platform / `charts/tenant`** is behind the Platform CRD: it cannot emit
  `spec.datastores`, `spec.identity.capabilities` or `spec.identity.directSecretReads`
  (nor `spec.attribution`), and `--set` on those paths is silently discarded. Until it
  is fixed, no chart-vended tenant can declare a datastore or a capability. The same
  gap exists in `agentctl platform new` and therefore in the portal, which renders the
  same chart.
- **eks-agent-platform / `charts/tenant/templates/NOTES.txt`** tells every operator to
  run `kubectl wait --for=condition=Ready platform/<name>` — the condition the
  operator never writes. It is the same bug phase 9 had, printed to a human on every
  tenant install.
- **landing-zone** has no `model-import` (or `agent-iam`, or `github-oidc`) live root
  outside `workload-development`. `agent-iam` is the one that bites: rackctl applies
  it by default, so no staging or production run can currently succeed. The leaves are
  bare root + `_envcommon` includes with `inputs = {}` and region/environment come from
  `live/root.hcl`, so they are byte-identical across environments.
- **An imported model is unreachable by a tenant until landing-zone AND
  eks-agent-platform change together.** landing-zone's `agent-iam` needs a variable that
  can express an imported-model ARN (e.g. `bedrock_allowed_imported_model_arns`,
  defaulting to `[]`, folded into `bedrock_baseline_invoke_resources`); *and* the
  operator's `bedrock-model-scoping` policy — a `Deny` with `NotResource` set to the
  expanded foundation-model/inference-profile list — has to admit it too. Either change
  alone leaves the route at `AccessDenied`.
- **landing-zone / `model-import`** — the versioned staging bucket has no
  `force_destroy`, so even a deliberate `terragrunt destroy` fails once weights are
  staged. Defensible for account substrate; worth documenting in the component header,
  since it is why rackctl refuses to destroy it.
- **landing-zone** — the *development* network leaf is now `network_mode = "adopt"`
  with a dependency on a `shared-network` unit rackctl never applies, while all three
  of rackctl's create-mode levers hard-reject adopt mode. `development` is rackctl's
  default environment. This needs a product decision (rackctl's create-mode assumption
  vs. the org's canonical adopt-mode reference leaf), not a code guess, and is
  deliberately untouched.

## Known-stale and deliberately untouched

Each is a separate campaign, listed so it is not mistaken for an oversight:

- The `fleet` phase runs `kubectl apply -f eks-fleet/crossplane.yaml` from the
  landing-zone checkout, which has no such directory; `engine.Repos` has no field for
  the `eks-fleet` repo and `acquire` never clones it.
- Seven `cluster-bootstrap` variables rackctl never passes — including the live
  inconsistency that `agentPlatform.enable: false` skips `agent-iam` while
  `enable_agent_platform` still defaults **true**, so ArgoCD installs an operator whose
  IAM role was never created.
- Roughly a dozen schema-only config fields (`addons.druid`, `addons.accelerators`,
  `cloud.identityCenter`, `cluster.ttlDays`, `cluster.systemNodes.*`,
  `agentPlatform.compliance`, …). `cluster.version: "1.35"` is actively misleading:
  landing-zone's `var.cluster_version` defaults to `1.36` and rackctl never injects it.
